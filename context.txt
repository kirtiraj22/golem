GOLEM — PROJECT CONTEXT / HANDOFF DOCUMENT
===========================================

1. WHAT WE ARE BUILDING
-----------------------
Golem is an on-chain, human-powered content evaluation and reward marketplace (hackathon project, Solana Devnet, native SOL only).

Flow:
 1. A company connects a Solana wallet and creates a campaign.
 2. It uploads images, sets a budget (lamports) and voting rules.
 3. It deposits the budget into an on-chain escrow (the Campaign PDA holds native SOL).
 4. Participants connect wallets and classify each image as AI_GENERATED or HUMAN_CREATED.
 5. One vote per wallet per image (enforced by the Vote PDA).
 6. After voting ends, the program computes the majority per image.
 7. Voters who matched the majority claim an equal share of that image's reward pool.
 8. After the claim deadline the company refunds everything remaining.

IMPORTANT PRODUCT RULE: Golem measures HUMAN CONSENSUS, not verified ground truth. Never present the majority result as objectively verified. There is NO AI model, AI inference or AI detection API anywhere in the system.

2. ARCHITECTURE
---------------
A) Solana program (Anchor 1.0.2) = single source of truth for campaigns, escrow, assets (+SHA-256 hashes), votes, vote counts, results, reward eligibility, claims, refunds.
B) Next.js 16 (App Router) + Supabase = application layer only: descriptions, image storage, profiles, discovery/filtering, cached on-chain data, tx history, analytics. Supabase is NEVER the authority for votes, results, rewards or payouts.
 - Never trust the frontend for vote counts, results, reward amounts or "tx succeeded" claims. Verify transactions and account state against Solana.
 - Images are stored in Supabase Storage; only the SHA-256 hash goes on-chain.
 - All user-authorized transactions are signed by the user's wallet. No server-side private key ever signs for a user.
 - Server-only privileged DB operations use SUPABASE_SECRET_KEY (never NEXT_PUBLIC_).
 - Wallet auth = signed challenge (expiry + one-time nonce) -> session token (stored hashed).

Account layouts (Anchor, 8-byte discriminator):
 Campaign: company Pubkey, campaign_id u64, total_budget u64, expected_asset_count u32, registered_asset_count u32, min_votes u64, voting_deadline i64, claim_deadline i64, status CampaignStatus, finalized_asset_count u32, total_claimed u64, bump u8
 Asset: campaign Pubkey, asset_index u32, content_hash [u8;32], ai_votes u64, human_votes u64, total_votes u64, result AssetResult, winning_votes u64, reward_pool u64, total_claimed u64, finalized bool, bump u8
 Vote: asset Pubkey, participant Pubkey, classification Classification, claimed bool, bump u8
Enums (IDL camelCase objects, e.g. { aiGenerated: {} }):
 CampaignStatus: Draft | Active | Closed | Settled
 Classification: AiGenerated | HumanCreated
 AssetResult: Pending | AiGenerated | HumanCreated | Tie | InsufficientVotes
Off-chain/DB string mapping: DRAFT/ACTIVE/CLOSED/SETTLED; AI_GENERATED/HUMAN_CREATED; PENDING/AI_GENERATED/HUMAN_CREATED/TIE/INSUFFICIENT_VOTES.

Events: CampaignCreated, AssetRegistered, CampaignFunded, VoteCast, CampaignClosed, AssetFinalized, RewardClaimed, CampaignRefunded.
Errors (GolemError): InvalidAssetCount, InvalidBudget, InvalidMinVotes, InvalidDeadlines, Unauthorized, InvalidCampaignStatus, AllAssetsRegistered, AssetsNotAllRegistered, InvalidAssetIndex, VotingNotOpen, VotingStillOpen, AssetCampaignMismatch, AssetAlreadyFinalized, AssetNotFinalized, NoRewardAvailable, NotWinningVote, AlreadyClaimed, ClaimWindowClosed, ClaimWindowOpen, AssetsNotFinalized, MathOverflow, InsufficientEscrow.

Key behaviours later stages depend on:
 - Assets must be registered sequentially: index 0,1,2,... (index must equal registered_asset_count). Max 500 assets per campaign.
 - Budget must be >= asset count (1 lamport per asset minimum).
 - Registration is allowed only in DRAFT; funding requires all assets registered and now < voting_deadline; funding transfers exactly total_budget and sets ACTIVE.
 - Voting only when ACTIVE and now < voting_deadline.
 - close_campaign: company any time while ACTIVE; anyone once now >= voting_deadline.
 - finalize_asset is permissionless; if the campaign is ACTIVE and the deadline has passed it also flips the campaign to CLOSED. Result rules: total_votes < min_votes -> InsufficientVotes; ai > human -> AiGenerated; human > ai -> HumanCreated; equal -> Tie.
 - Reward pool per asset = floor(total_budget / expected_asset_count), set at finalization for AiGenerated/HumanCreated results only (Tie/Insufficient => pool 0, claims rejected).
 - Per-voter reward = floor(reward_pool / winning_votes). Claims require CLOSED campaign, finalized asset, now <= claim_deadline, winning vote, not already claimed. Escrow rent-exempt minimum is preserved.
 - refund_campaign: company only, status CLOSED, now > claim_deadline, finalized_asset_count == expected_asset_count; sends all lamports above rent-exempt minimum to the company and sets SETTLED. (Consequence: the company must ensure every asset gets finalized, which anyone can do.)
 - Participants pay rent for their Vote PDA; company pays rent for Campaign and Asset PDAs.

5. SUPABASE SCHEMA (DELIVERED, STAGE 2)
---------------------------------------
Migrations in supabase/migrations/ (apply in this order):
 20260101000000_golem_schema.sql  -> profiles, campaign_metadata, asset_metadata, chain_transactions, triggers (updated_at, asset index bound)
 20260101000100_golem_auth.sql    -> auth_challenges, wallet_sessions, purge_expired_auth()
 20260101000200_golem_rls.sql     -> RLS enabled on all tables, grants, public read policies
 20260101000300_golem_storage.sql -> private bucket "campaign-assets" (10 MB limit; jpeg/png/webp) + select policy
Types: web/src/lib/db/database.types.ts (hand-written Database type; can be replaced later via `supabase gen types typescript`).

Design decisions:
 - Only the service role (SUPABASE_SECRET_KEY, server-side) can write. anon/authenticated only SELECT, and only rows belonging to campaigns with is_listed = true (profiles are public). auth_challenges and wallet_sessions are completely inaccessible to anon/authenticated.
 - is_listed must only be set true by the API after verifying on-chain that the campaign is funded/active.
 - u64 values (campaign_id, lamports, votes) are bigint columns constrained to <= 2^53-1 so they are safe as JS numbers. The client MUST generate campaign_id within 0..2^53-1 (e.g. Date.now()).
 - campaign_metadata.campaign_pubkey and asset_metadata.asset_pubkey link rows to on-chain accounts. cached_* columns are caches of on-chain state, refreshed by the API from Solana; they are not authoritative.
 - asset_metadata.asset_index is assigned by the API sequentially per campaign and must equal the on-chain index. Unique (campaign_pubkey, content_hash) prevents duplicate images per campaign.
 - Storage path convention: <campaign_pubkey>/<sha256hex>.<jpg|png|webp>. Bucket is private; clients get signed URLs; the select policy only exposes objects of listed campaigns. Uploads happen server-side only.
 - chain_transactions has one row per (signature, instruction_index); only verified successful transactions are inserted.
 - Challenge consumption must be one atomic statement: UPDATE auth_challenges SET consumed_at = now() WHERE nonce = $1 AND consumed_at IS NULL AND expires_at > now() RETURNING *.
 - Session tokens: random 32+ bytes, only the SHA-256 hex is stored in wallet_sessions.token_hash.
